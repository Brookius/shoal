## 1. The job to be done

Today a dive is a flat set of scalars (max/avg depth, bottom time, safety stop). A
**dive profile** adds the continuous time-vs-depth curve the computer recorded.
Why it's worth doing:

- **Engagement** — seeing your dive as a curve is satisfying; it's why dive
  computers show it, and another reason to re-open a logged dive.
- **Safety read-back** — ascent-rate and safety-stop quality are visible in a curve,
  invisible in scalars.
- **OBIS / Darwin Core** — a depth profile on an Event record adds scientific
  context (*which phase of the dive* a species was seen).
- **Backwards-compatible** — the existing safety/deco-stop scalar fields (v2.14)
  stay as the **summary layer**; the profile is additive.

## 2. The premise — why this is now small

The whole reason this can be scaled right back: **someone else already extracts the
data.** BLE → `libdivecomputer` → UDDF is a solved problem in native apps. Dive
Exporter (and Subsurface, MacDive, vendor software) connects to the hardware and
writes a portable `.uddf`. We **never** touch hardware, BLE, or libdivecomputer.

Division of labour is clean: those tools are *not* logbooks (Dive Exporter
explicitly stores no sites/buddies/photos) — they emit the **profile + computer
metadata**. Dive Log is the logbook (site, buddy, species, notes). So the natural
flow is: the user exports a `.uddf` from whatever tool, brings it to Dive Log
(AirDrop / Files / a synced folder), and we **attach its profile to the dive they
already logged.** Producer-agnostic, format-specific: **UDDF in.**

## 3. Scope (minimal — do not exceed)

**In:** parse one `.uddf` (which may contain several dives) → match each dive to a
logged dive by date/time → attach the profile as a sidecar → render a beautiful
profile chart in the dive file.

**Out:**
- Hardware / BLE / libdivecomputer — solved elsewhere.
- Other formats — no Subsurface XML, CSV, FIT, SQLite, HealthKit. UDDF only.
- Deco recomputation — no CNS/OTU/gradient-factor/ceiling recompute.
- Tech-diver overlays — no per-cell PPO₂, no multi-tank pressure curves, no
  deco-ceiling traces. (These are exactly what Dive Exporter is proud of — and
  exactly what *our* persona doesn't need.)
- Profile editing (trim/merge).

**Constraints:** vanilla JS, `DOMParser`, no build tools, no runtime Python, no
backend. `esc()` on render + numeric coercion on every imported value (external
input).

## 4. Flow

```
file picker (.uddf) → parseUddf() → for each dive: matchToLoggedDive()
                    → attach (or skip) → writeProfileSidecar() → renderProfileChart()
```

- **Match — physical signature first, clock second.** For each UDDF dive, **rank the
  logged dives by a lightweight combined score and auto-suggest the top match** —
  auto-attach only when it's a clear winner (high score + margin over the runner-up);
  otherwise show a short ranked list to confirm or pick. Signals, in priority:
  - **Primary — max depth + bottom time (clock-independent).** These are physical
    facts of the dive, recorded the same whether or not the computer's clock is
    right. Fuzzy-match with tolerances, because the logged values are user-rounded
    (e.g. depth ±1–2 m, time ±2–3 min).
  - **Secondary — date + entry time (corroborating).** It *raises* confidence when it
    agrees but **never vetoes** a strong depth+time match — so a wrong or reset clock
    simply stops contributing rather than breaking the match.
  - **Tiebreaker for a batch import — chronological order.** UDDF dives come in
    sequence, so dive N should map *after* dive N-1's match; this separates look-alike
    dives (~18 m / 45 min) even when the clock is useless.
  - Overwrite-confirm if the dive already has a profile; "not this one / skip" always
    available.

  *Why this order:* a real history (dives ~30–150) had the computer clock reset
  during periods of inactivity — date/time unreliable — but bottom time and max depth
  were copied diligently. Physical signature is the backbone; the clock is evidence,
  not the key.
- **Multi-dive file** (a whole trip export): apply the same per-dive auto-suggest down
  the list; keep the review UI lean — a ranked pick per dive, not a heavy wizard.
- **No match:** skip by default; optionally offer "create a new dive from this
  profile" (pre-fills depth/time/date from the UDDF, user fills the rest) — a small
  secondary path, not required for v1.

## 5. Data model

```javascript
profile: {
  source: 'uddf',
  computer: 'Shearwater Teric',   // free text, from the file
  startedAt: '2026-05-07T09:12:00',
  waypoints: [ { t: 0, d: 0 }, { t: 30, d: 5.2, temp: 28 }, … ], // t=sec, d=metres
  events: [ { t: 3120, type: 'safetystop' } ],                   // optional
  imported: '2026-05-28',
}
```

- Stored as a **`<dive-basename>.profile.json` sidecar joined on `uid`**, mirroring
  the footage sidecar (bulky data lives outside the `.md`; ≤~50 KB). Scalars stay in
  the `.md` frontmatter as the summary layer.
- **Renumber / rename safety:** the profile sidecar inherits the join model and
  coordinated-rename handling in **`BRIEF-sidecar-filename-hygiene.md`** — that work
  should land first (it also fixes footage). `deleteDive` must remove
  `.profile.json` too.

## 6. Parsing UDDF

- `new DOMParser().parseFromString(text, 'application/xml')`, walk the tree. Map
  `<samples>/<waypoint>`: `<divetime>`→`t`, `<depth>`→`d`, optional `<temperature>`
  (Kelvin → °C). Gas switches / alarms → `events[]`.
- Also surface **`maxDepth`** (`<greatestdepth>`, or the max of waypoint depths) and
  **`duration`** (`<diveduration>`, or the last waypoint `t`) on the parsed result —
  these are the **primary match keys** (§4), so they must be reliable even when the
  file's timestamp is wrong.
- **`valueTransforms`** — one helper: Kelvin→°C, tolerant date parsing (computers
  timestamp local vs UTC inconsistently — matching must cope).
- **Downsample / cap** — cap waypoint count (downsample to ~1 / 10 s if denser) and
  reject absurdly large files, to avoid OOM on mobile.
- **Security** — `DOMParser` doesn't resolve external entities (no XXE); still treat
  every parsed string/number as untrusted.

## 7. Display — the centrepiece ("display beautifully")

The emphasis of the scaled-back brief. A clean, on-brand **SVG profile chart** in
the dive file (consistent with the existing SVG charts in `stats.js`, no new dep).
Design study done 2026-07-06 against five reference cases
(`mockups/Dive Profile Chart mockup.pdf`) before building — see `DECISIONS.md` →
"Dive computer profile import" for the resolved calls below.

- **Depth curve** — Y = depth, **inverted** (0 at top); X = time (minutes). Shade
  under the curve so it reads like water depth.
- **On-brand** — Warm-White surface, Deep-Water (`#1C3030`) curve, mono axis labels,
  the three-size type scale. It should feel like the journal/dive-file aesthetic,
  not a cockpit instrument.
- **One colour mechanic only — NDL headroom.** The curve tints from a calm blue
  (time to spare) toward red as no-decompression limit nears zero, hard red once
  it hits. Needs per-waypoint `<nodecotime>`, which not every export carries (see
  DECISIONS.md) — absent that data, the curve just renders in the plain on-brand
  colour, same as when temperature is absent. Ascent-rate colour coding was
  explored in the design study and deliberately cut — one colour signal, not two.
  The safety-stop phase still gets a gentle (uncoloured) highlight from the
  already-captured `safetystop` events.
- **Temperature as two anchored points, not a trace.** Surface temp (first
  waypoint) and minimum temp, labelled directly on the curve at the moments they
  occurred — not a second polyline or a continuous right-hand axis.
- **Smoothing is fixed** — light corner-rounding only, never resamples away real
  texture (sawtooth/yo-yo profiles stay honest). No user-facing Smoothing or
  Curve-weight control.
- **Static first** — a clean rendered curve with axes is enough; light interactivity
  (touch/hover to read depth @ time) can come later.
- **Placement** — replaces the existing floating stat-bubble band (v2.72.2) on
  any dive with a profile; the chart's own readout strip (max/duration/avg
  depth/min temp, SAC beside gas) carries those numbers instead. Dives without a
  profile keep today's stat-bubble treatment unchanged. Visibility stays on the
  Conditions card either way — it's a condition, not something the profile
  measures.

## 10. Where to learn safely

- **UDDF 3.2 spec (uddf.org)** — the authoritative, licence-clean implementation
  source. Write the parser from this.
- `uddf-swift` (open-sourced by Dive Exporter's author) — a handy *reference* for
  field/structure questions, but it's Swift; reimplement in JS from the spec.
- Submersion's UDDF design docs — read for gotchas (event parity, etc.); facts and
  approach only, no code.

## 11. When to build

After the dive-file layout settles (notes-as-journal §4d) — the chart shares that
surface. The parser is the main effort and it's just XML.
