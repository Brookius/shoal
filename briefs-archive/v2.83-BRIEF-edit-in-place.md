# v2.83 — Edit in place: retire the edit modal, edit on the Log panel

## Problem

The edit modal is a hand-maintained second copy of the log form. `openEdit()`
(app.js) regenerated ~330 lines of `e-`-prefixed markup as a template literal
on every open; `saveEdit()` mirrored `saveDive()`'s 35-field read list;
`modalSightings` mirrored `sightings`; a second Leaflet instance had its own
lifecycle. Every field, layout, or control change had to land twice — the
changelog shows the tax being paid repeatedly ("applies to both form and edit
modal"), and DECISIONS.md's dive-type entry cites the duplication as a reason
a data-model fix got parked.

Worse, embedding a page-shaped form inside a fixed overlay produced a
recurring *class* of stacking-context bugs — autocomplete dropdowns clipped
by `#em-*` sections, Leaflet panes painting over fixed UI, the mobile species
picker rendering *behind* the modal (`z-index` 600 vs 1000). Four changelog
entries, one root cause.

The modal's one real payoff — "close it and your dive file is still there" —
only exists on desktop. On mobile the modal is already full-screen.

## Decision

**Edit happens on the Log panel.** The ✎ buttons prefill the existing `f-`
form from the dive, navigate to Log with an unmissable edit banner, and the
save path updates the dive in place. The modal, its template, its parallel
save path, its mirror state, and its overlay-stack case are all deleted.

The `logform.js` prefix system **stays** — it's parameterisation, not
duplication, and costs nothing. Only its `'e'` consumers (`lfInitEditModal`,
`lfDestroyEditMap`, the `em-dive` branch) go.

## Design

### State

One flag: `editingId` (already existed for the modal; now means "the Log
panel is in edit mode for this dive id"). `editingId === null` ⇒ normal
logging. No second flag, no mirror arrays — edit mode uses `sightings` and
the `f-` fields directly.

### Entry — `openEdit(id)` (name kept; all four inline ✎ call sites unchanged)

1. **No dirty guard — ✎ always jumps straight into edit, silently
   discarding any unsaved Log-page draft.** A confirm-before-discard guard
   was built, shipped, and pulled within the same round of manual testing.
   It checked a hand-maintained allowlist of "content" fields (excluding
   carry-forwards like date/trip/region/watertype/liveaboard and
   auto-prefills like default safety stops) plus `sightings.length` and a
   special-cased gas-mix check. It **twice** missed real fields in practice
   — first Operator leaking on *exit* (a separate, real bug, fixed —see
   "No field leaks" below), then Current/Gas/deco-stop missing from the
   *entry* guard's allowlist entirely, letting a real draft through with no
   warning. Even after that fix, a manual retest with Site + a sighting
   (both covered since the very first version) still showed no prompt —
   likely a stale `cargo tauri dev` session rather than a third gap, but by
   that point the mechanism had cost two rounds of debugging for a problem
   the rest of the app doesn't otherwise solve: switching to Stats or
   Species while a draft sits on Log discards it just as silently, with no
   confirm at all. Luke's own call: drop it. ✎ is now consistent with every
   other panel switch, and an accidental premature edit is one tap to
   re-open and keep filling in — cheap, now that edit mode exists at all.
2. **Discard any pending UDDF prefill** — `_pendingNewDiveProfile = null`.
   If the form content being discarded came from a dive-computer import, the
   captured profile belonged to that discarded dive and must not survive to
   attach to something else later.
3. `editingId = id`, then `show('log')`. The unified `show()` patch already
   force-closes any open overlay (the dive file the user tapped ✎ inside),
   and pushes the `{panel:'log'}` history entry — back-gesture wiring comes
   for free.
4. Prefill (`_prefillLogFormFromDive`): set every canonical `f-` input from
   the dive (same field list `saveDive()` reads), deep-copy `marine` into
   `sightings`, `renderSightings()`, repaint visual controls via the
   existing `lfSyncFromFields()`, centre the pin map via `lfSetPin('f',…)`
   when GPS exists, refresh all seven section summary chips, collapse all
   sections and open **Marine life** (modal parity — the most common edit
   target stays one tap away), scroll to top.
5. Edit-mode UI: `#panel-log` gets class `editing` (CSS hides the UDDF
   banner/status/picker/review, the `#md-output-area` confirm bar, and the
   intro subtitle — all "new dive" affordances that would either mislead or,
   in the UDDF case, actively overwrite the edit); the page title flips to
   "Edit a dive"; a banner appears — `✎ Editing dive #21 — Hin Daeng` with a
   **Cancel** button; both save buttons relabel to "Save changes".

### Exit

- **Cancel** (banner button): `_clearEditMode()` then `history.back()` — the
  popstate handler restores the panel the user came from (History), scroll
  position included via `_panelScrollY`.
- **Back gesture / Escape-free navigation**: any `show()` to a non-log panel
  while `editingId` is set clears edit mode (one line inside the single
  unified `show()` patch, per the standing "no new show() patches" rule).
  This is the mode-leak mitigation: there is **no path that leaves the Log
  panel with edit mode still armed**, so "log a new dive" can never silently
  overwrite an old one.
- **Save**: see below; ends with `_clearEditMode()` + `history.back()`.

Both exits land on **History** (timeline re-rendered with the updated card),
never back inside the dive file — deliberately, because reopening the dive
file after `history.back()` needs async popstate choreography, and the old
modal's "return to the dive file" actually returned to a *stale* render
(saveEdit never re-rendered the open dive file). One predictable landing
beats two, one of which lies. Escape-to-cancel was also deliberately not
wired: a document-level Escape would collide with the species panel and
autocomplete dropdowns' own Escape handling.

`_clearEditMode()` fully resets the form (shared `_resetLogFormFull()`,
factored out of `_afterSaveReset` so post-save reset behaviour is unchanged)
— including the carry-forward fields, since carrying an *edited 2023 dive's*
date/trip into the next new-dive form would be wrong.

### Save — one `saveDive()`, two branches

The field-read block is now written once. Then:

- **New dive** (unchanged): mint `id`/`uid`, `videos: []`, unshift, set
  `lastSavedDiveId`, show filename confirm bar, `_afterSaveReset`, button
  success animation.
- **Edit** (`editingId !== null`): find the dive, merge
  `{ ...existing, ...fields }` — the spread-preserve semantics of the old
  `saveEdit`, so everything not on the form (`id`, `uid`, `videos`,
  `_filename`, anything future) survives; **no** unshift, **no**
  `lastSavedDiveId`, **no** confirm bar, **no** `_afterSaveReset`, **no**
  divenum `dives.length + 1` fallback. Then `_pendingSync`, localStorage,
  autocomplete cache, backend push, `renderHistory()`, clear edit mode,
  `history.back()`.

Renames (divenum/site changed) need nothing new — `writeToFolder`/
`pushToObsidian` already compare `canonicalFilename()` against `_filename`
on every save and run the coordinated rename.

**Pending-profile gate** (risk: a UDDF profile attaching to the wrong dive).
The profile.js `saveDive` patch guarded on `lastSavedDiveId != null` — which
an edit-save leaves *stale*, pointing at some earlier dive. The patch now
records `editingId !== null` **before** calling through (the inner save
clears it) and skips attachment entirely on an edit save. Belt-and-braces
with the discard in openEdit step 2.

### Delete

The modal footer's Delete (native `confirm()`) is gone with the modal. The
timeline trash icon and dive-file "more" menu already cover deletion via the
`armDelete` two-click pattern — removing the modal removes the one
inconsistent delete UX rather than losing a capability.

## What died

- app.js: the `openEdit` template (replaced by prefill + banner logic),
  `saveEdit`, `ge`, `calcExitTimeModal`, `closeModal`, `closeModalDirect`,
  `handleOverlayClick`, `toggleModalMarineLegend`, `confirmDelete`,
  `modalSightings` + all six modal marine functions, the modal
  outside-click listener, the `editModal` case in `_closeOverlayDirect`,
  `deleteDive`'s `fromModal` parameter.
- species.js: the modal species panel block (`_modalPanelGroup`,
  `_renderModalPanel`, `hideModalDropdown`, modal browse tabs).
- logform.js: `lfInitEditModal`, `lfDestroyEditMap`, the `'e'` branches.
- index.html: the `#edit-modal` markup.
- styles.css: selectors that referenced now-nonexistent modal ids.
  `.modal-overlay`/`.modal` themselves **stay** — shared by the species
  profile modal and the welcome overlay.

## Smoke test (manual, phone + desktop)

Each numbered item maps to a flagged risk.

1. **Round-trip fidelity**: open a fully-populated dive (GPS, sightings with
   abundance, stops, notes title) → ✎ → change nothing → Save changes →
   reopen. Every field identical; `.md` in the folder rewritten but
   equivalent; footage/profile sidecars untouched.
2. **Merge-preserve**: edit a dive that has footage clips and a profile
   chart → change only the notes → save → clips still play, chart still
   renders (`videos`/`uid`/`_filename` survived the merge).
3. **Rename path**: edit a dive's site name → save → folder shows the new
   canonical filename, old one gone, sidecars renamed with it.
4. **No dirty guard, by design**: start logging a new dive (site + a
   sighting) → History → ✎ any dive → **no** confirm, edit opens
   immediately with the dive's data. Then Log → the draft is gone (matches
   what already happens switching to Stats/Species with an unsaved draft).
5. **Mode leak**: enter edit → navigate to Stats via nav bar → back to Log.
   Form is blank, title says "Log a dive", save button says "Save dive" —
   then save a new dive and confirm it *created* one rather than
   overwriting the edited dive.
6. **Back gesture (Android)**: enter edit from the timeline → swipe back →
   lands on History at the same scroll position, edit mode cleared.
7. **From the dive file**: open a dive file → ✎ → banner shows the right
   dive → Cancel → lands on History (dive file closed, not stale).
8. **Mobile species picker**: in edit mode, tap the Marine search → the
   full-screen picker opens *in front* (the original bug) → pick a species
   → it lands in the sighting list → save → persisted.
9. **Pending-profile gate**: import a UDDF on the Log page (form prefills)
   → without saving, ✎ an old dive → confirm discard → edit and save. The
   old dive must have **no** profile chart. Then log a new dive normally —
   no leftover profile attaches.
10. **Sightings isolation**: edit a dive, *remove* a sighting, Cancel → the
    dive still has the sighting (edits worked on a copy).
11. **No field leaks into the next new dive**: edit a dive with an Operator
    set → save → log a new dive. The Operator field must be blank. (Caught
    in Luke's first desktop pass: `f-liveaboard` was missing from the reset
    list — it had never been in `_afterSaveReset`'s either, invisibly,
    because the modal's separate `e-` fields never wrote into the form.
    Operator still deliberately carries across consecutive *new*-dive saves,
    like trip/region.)
## Out of scope / revisit

- Returning to the dive file after save (needs popstate choreography; add
  only if landing on History feels wrong in practice).
- Escape-to-cancel on desktop.
- The `1500 ms` "✓ Saved" button animation on edit saves — the panel
  navigates away immediately, so it was dropped rather than raced.
