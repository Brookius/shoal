# v2.8 — Species-profile footage player

**Goal:** turn the species profile from a passive list of clip names into a place you
*watch your own footage* of each animal — the footage manager's distinctive magic, and
a genuine differentiator vs other dive apps.

## Why it's multi-phase (the core insight)
Playback is a **source problem, not a UI problem.** Watching "your clip of this turtle"
needs the clip's video resolved (proxy or original), the folder/proxies *connected*, and
a seek to the clip timestamp. The footage modal **already solves all of this**
(`openFootage` watch mode, `resolveVideoUrl`, proxy→original fallback, seek-to-time). The
species profile has none of it (passive text rows). **Discipline: reuse the modal's engine
first, build the bespoke inline player last.** The trap is starting with Phase 3 because
it's "the vision" — that front-loads the hardest UI before the data/behaviour is proven.

## Cross-cutting constraint (applies to every phase)
**This is a Tauri-app feature for now.** Playback needs the local video/proxy files, which
only the macOS app reliably reaches (`isShell()`); the web build doesn't open footage at
all (see v2.7 §8). So every phase here is **Tauri-scoped**. Cross-platform watching —
browser and mobile streaming tagged footage — is a **future capability gated on cloud
hosting** (Backblaze B2 / pluggable provider); when it lands, this same species-profile
player becomes the cross-platform viewer. Until then there is **no web/mobile watch path**
— do not build File-System-Access playback into the web build.

## Current state (grounding — verified this session)
- Clips live in the **footage sidecar**, keyed by `scientificName || customId`; each clip is
  `{time, note, sources[]}`, sources `{role:proxy|original, kind:local, ref}`. Merged into
  memory at load.
- Species profile (`js/album.js`): clip rows render via `_clipRowHtml(c)` (≈L407), built from
  `_sightingClips(m)` (≈L69); supports 0/1/N clips with a `toggleAlbumClips` expander. Rows
  are **display-only** — the ▶ glyph is decorative, nothing plays.
- Footage modal (`js/footage.js`): `openFootage(diveId, opts)` (≈L111) has a **Watch mode**
  ("▶ on species → Watch", ≈L125). `resolveVideoUrl(clip, opts)` (`js/video.js`) is the URL
  seam. Proxy match is by **filename stem** (`_proxyUrls`), pooled across connected folders.

## Phase 0 — Discoverability — ✅ DONE (shipped in v2.65)
Ever-present, greyed footage 🎬 (timeline card + dive file) with a hover tooltip when a dive
has no footage. `.footage.empty` in styles.css; `hasFootage`/`footageTip` in history.js.

## Phase 1 — Launch the existing player at a clip  (low–moderate risk)
Wire each species-profile clip row to open the footage modal in Watch mode focused on *that*
clip (right video, seeked to `clip.time`).
- `album.js`: make `_clipRowHtml` rows clickable → `openFootage(diveId, {clip})` (or equiv).
- Carry the **diveId** through `_sightingClips` — clips are aggregated across dives per
  species, so each row must know which dive it came from.
- **OPEN Q (resolve first):** does Watch mode already deep-link to a specific clip, or does
  `openFootage` need a `{clip}`/`{seekTo}` opt? Check `footage.js` before building.
- Not-connected state: if `resolveVideoUrl` returns null, the row offers "Connect footage
  folder" rather than a dead play.
- **Accept:** from a species profile, clicking a clip opens the player and plays from the
  right timestamp; with no folder connected you get a connect prompt, not a dead click.
- **Caveat (acceptable for P1):** opens the full modal (a context switch), not inline.

## Phase 2 — Thumbnails / the album look  (moderate; asset/data phase)
A poster frame per clip so the profile becomes a visual grid of "your clips of this species".
- Generate at **proxy time** (capture a frame at `clip.time`) — preferred — or lazily via a
  hidden `<video>` seek + canvas when the folder's connected.
- **OPEN Q:** where thumbs live — a `thumbs/` folder beside proxies (clean, matched by
  filename stem like proxies; more file management) vs a data-URI in the sidecar (simpler,
  but bloats the sidecar). Lean: `thumbs/` folder.
- `album.js`: clip rows → thumbnail tiles; reuse the existing 0/1/N + expander logic.
- **Accept:** each clip shows a poster; the grid reads as a personal video album of the animal.

## Phase 3 — Inline playback + card rethink  (most work; do last)
Play in place — no modal context switch.
- Lightbox or embedded mini-player in the species profile; prev/next across *all* clips of
  that species; reuse `resolveVideoUrl` + seek logic (extract from the modal if needed).
- This is the species-card redesign flagged as a dependency.
- Keep the not-connected and mobile states first-class.
- **Accept:** tap a clip → it plays in the profile; step through every clip of that species
  without leaving; clean states when sources/folders are absent.

## Out of scope / non-goals
- No new sync backend or cloud video hosting (`resolveVideoUrl` reserves cloud kinds — not now).
- No re-encoding changes (proxies stay on the existing LGPL ffmpeg sidecar / `make-proxies`).
- No mobile playback of large originals (desktop-first; mobile = list + "watch on desktop").
- **Do not touch** the frozen nested-YAML clip read-fallback in `markdown.js`.

## Sequencing
0 (done) → 1 → 2 → 3. Each phase is independently shippable. Resolve the Phase-1 OPEN Q
(does Watch mode deep-link to a clip?) before starting. Bump `sw.js` cache whenever a shell
file changes.
