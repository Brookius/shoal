> **Status: draft for review.** Facts below were verified May 2026 (Tauri
> v2.11.2) and pinned in ROADMAP.md → "Desktop + Mobile App (Tauri)" and
> DECISIONS.md — **do not re-research without cause.** This brief turns that

## 1. The job to be done

The browser proxy workflow (v2.38) works but is techy: install ffmpeg via
Homebrew, paste a `curl | bash` one-liner into Terminal inside the originals
folder, then connect the proxies folder through the File System Access
picker. Powerful for the builder; a non-starter for anyone else.

The desktop shell collapses that into **one button**: Tauri bundles ffmpeg as
a sidecar binary, the app picks the originals folder with a native dialog and
runs the re-encode itself with a progress bar. Secondary wins that come free
with the shell:

- **Real filesystem** — vault/folder sync without File System Access API
  quirks (no Brave block, no permission re-grants, no storage caps; can point
  at a NAS or external drive).
- **Distribution at £0** — un-notarized `.dmg` from GitHub Releases (the
  MLX/llama.cpp model): one-time "Open Anyway" in System Settings, runs
  forever after. Notarization ($99/yr) is a drop-in upgrade later if ever
  warranted.

The browser build remains the dev environment, the free Cloudflare deploy,
and the fallback. The shell *wraps* it — it never forks it.

## 2. Hard scope boundaries (do not exceed)

- **macOS desktop only.** No Windows (SmartScreen pain, out of scope for a
  Mac-first personal tool). No mobile target yet — Tauri-mobile is the
  *plan* for the eventual phone app, but it gets validated at its own
  moment (DECISIONS.md), not smuggled in here.
- **No web-code rewrite.** The same `index.html` + `js/` + `css/` runs in
  both browser and shell. Differences live behind capability seams only
  (feature-check + swap, the `resolveVideoUrl` pattern). If a phase needs a
  web-code change that isn't a seam, stop and re-scope.
- **No build step for the web code.** Tauri's `frontendDist` points at the
  repo root's static files as-is. The Rust/Tauri toolchain builds the
  *desktop artifact only* — this is the sanctioned packaging exception to
  the no-build-tools decision (DECISIONS.md).
- **No App Store, no notarization, no auto-update** in v2.5. GitHub
  Releases + manual download. Auto-update is a later nicety, not a phase.
- **No new features.** The shell ships exactly the browser feature set with
  the seams swapped. Feature work continues in the browser build.

## 3. Architectural constraints (carry-forward)

- Classic ordered `<script src>` files, no ES modules, functions global.
- `esc()` for any new innerHTML interpolation (v2.39x security baseline).
- The CSP currently lives in `_headers` (Cloudflare-only). The shell must
  port an equivalent CSP into `tauri.conf.json → app.security.csp`.
- Theme system: `.theme-*` token-override classes; shell chrome (titlebar
  etc.) stays native — no custom window chrome in v2.5.
- Sidecar JSON / uid / customId model unchanged — the shell reads and
  writes the same vault files the browser build does.

## 4. The capability seams (what actually differs in-shell)

Detection: a single helper, e.g. `isShell()` → `!!window.__TAURI__`, defined
once in app.js. Every divergence goes through it — never scatter raw
`window.__TAURI__` checks.

| Seam | Browser today | Shell behaviour |
|---|---|---|
| `transcodeProxies()` | copies `curl \| bash` one-liner (js/video.js:493) | native folder dialog → `Command.sidecar('ffmpeg')` per file → progress UI → proxies land in `./proxies/` beside originals |
| Folder sync (vault read/write) | File System Access API (Chrome/Edge only) | Tauri `fs` + `dialog` plugins — persistent path in localStorage, no re-grant ceremony |
| Service worker | registered for offline shell | **skip registration in-shell** (files are local; SW on a `tauri://` origin is useless at best) |
| `resolveVideoUrl` | proxy folder handle / file picker | unchanged interface; backing handle comes from the fs seam |
| Obsidian REST (`http://127.0.0.1:27123`) | direct fetch | same fetch — **but validate early** (see risks) |

## 5. Risks to validate in phase 2.51 (before building on top)

**✅ Validated 2026-06-13 (with Sonnet) — all four pass.** Recorded here to
close phase 2.41's gate; the build proceeded on the strength of these.

1. **WebKit rendering.** The shell uses WKWebView, not Blink. Smoke-test
   every panel: form, history timeline, stats charts, map (vendored
   Leaflet), footage modal (dark theme, IUCN chips), video playback —
   especially `blob:` URLs and `<video>` seeking on proxy files.
2. **Loopback HTTP from the shell.** The webview origin is `tauri://` —
   confirm `fetch('http://127.0.0.1:27123')` works. macOS App Transport
   Security may require the local-networking exception in the bundle
   config. If it's blocked, the fix is config, not code.
3. **localStorage persistence** in WKWebView across app restarts and app
   *updates* (replace the .app, relaunch, data intact). All dive data on
   the shell rides on this until folder sync is connected.
4. **CSP port** — confirm the `tauri.conf.json` CSP doesn't break inline
   handlers (`'unsafe-inline'` still required) or `blob:` media.

All four passed; the rest was low-risk plumbing as predicted. (Electron
remains the last-resort fallback only if a future WKWebView regression appears.)

## 6. ffmpeg sidecar — the headline feature

- Declare in `tauri.conf.json → bundle.externalBin` with per-target binary
  suffix (`ffmpeg-aarch64-apple-darwin` for Apple Silicon; Intel build only
  if ever requested).
- Shell-exec **capability with argument validators** — allow exactly the
  re-encode argument shape `make-proxies.command` uses today (1080p,
  identical timeline), nothing else. No free-form args from JS.
- UI: the existing 📋 script button becomes **"Generate proxies…"**
  in-shell — native dialog picks the originals folder, files run
  sequentially, per-file progress (parse ffmpeg stderr time= against
  duration), cancel button, summary line on completion.
- Output contract identical to the script: `./proxies/<name>.mp4` beside
  the originals, so `resolveVideoUrl` and the proxy-folder connect flow
  need zero changes.
- ffmpeg licence: ship an LGPL build (or note GPL in an in-app credits
  line) — one-line task, not a phase.

## 8. Decision log (locked — do not re-litigate)

- **Tauri over Electron** — sidecar support, ~8 MB vs ~150 MB, and the
  same toolchain later covers mobile. WebKit re-test is the accepted cost.
- **Un-notarized GitHub distribution** — £0, MLX model; notarize later
  only if the audience grows.
- **Capacitor demoted to mobile fallback** — only if Tauri-mobile's `fs`
  plugin fails real Android field-logging validation (future, not v2.5).
- **Browser build stays primary** — deployed, build-free, and the
  fallback; the shell is packaging, not a platform migration.
- **ffmpeg.wasm rejected** (v2.3) — stands; the app itself never
  transcodes in-browser.

## 9. Post-build review (2.5 shipped — findings + resolutions, 2026-06-13)

The shell shipped (commit `2.5`) and is faithful to the brief; the review
below records what was corrected afterward so the brief stays the source of
truth.

### 🔴 ffmpeg portability + GPL — fixed (now LGPL/VideoToolbox)
The committed sidecar was the **dynamically-linked Homebrew ffmpeg** — `otool -L`
showed ~20 `/opt/homebrew/...` dylib deps, so it would `dyld: Library not
loaded`-crash on any Mac without those exact Homebrew packages — *and* it was
**GPL** (libx264/x265), which is App-Store-incompatible and carries a
source-offer obligation.

**Both problems solved at once by building LGPL from source.**
`src-tauri/build-ffmpeg.sh` downloads the pinned ffmpeg **8.1.1** source (sha256
cross-verified against Homebrew's checksum), configures `--disable-gpl` with
**no** libx264/x265, and compiles a **static single-file** binary that encodes
H.264 via Apple **VideoToolbox** (`h264_videotoolbox`) + native LGPL aac.
Results, all verified locally:
- License: configure reports *"LGPL version 2.1 or later"*; `-version` shows no
  `--enable-gpl`, no `libx264` → **GPL-free, App-Store-eligible, no source offer
  needed**.
- `otool -L` shows **only** `/usr/lib` + `/System` frameworks → one portable
  file. The earlier dylib-bundling, `src-tauri/frameworks/`, and
  `bundle.macOS.frameworks` were **removed**.
- A real 1080p `h264_videotoolbox` + `aac` transcode produces valid H.264
  High/avc1 output.

`run_transcode` now encodes `h264_videotoolbox -b:v 5000k -allow_sw 1 -tag:v
avc1`. Binary is git-ignored, built on demand (script no-ops when present;
`FORCE=1` rebuilds). **Final gate (user-side): `cargo tauri build` + launch the
`.dmg` on a clean Mac.** Quality note: VideoToolbox H.264 is marginally below
libx264 at a given bitrate — fine for review proxies, and hardware-accelerated.

### 🟡 Web build step — ratified (was a brief deviation)
Actual `frontendDist: "../webdist"` + `prepare-web.sh`, not the brief's
`frontendDist: "../"` / no-build-step. **Ratified** — it keeps briefs, mockups,
and `.git` out of the bundle. **Maintenance tax:** any *new* top-level web
asset (js/css/dir) must be added to `prepare-web.sh`'s copy list, same class of
chore as the `sw.js` SHELL list.

### 🟡 Security — shell capability tightened
`capabilities/default.json` granted `shell:allow-spawn` + `shell:allow-kill`,
but the frontend only ever calls **custom Rust commands** (`run_transcode`,
`pick_folder`, …) via `invoke` — never the shell plugin directly. Removed both
(the Rust `app.shell().sidecar()` call isn't gated by JS capabilities). The
brief's "no free-form args from JS" requirement is met in Rust: `run_transcode`
hard-codes the encode args and takes only a folder path. **Needs a rebuild to
confirm transcode still works** (expected: it does).

### 🟢 Accepted breadth (conscious, not accidental)
- Custom fs commands (`write_text_file`/`remove_file`/`list_md_files`) take any
  path JS passes — broader than the browser's per-folder-gated FSA API, but
  acceptable for a personal tool. Scope to the chosen vault root later if shared
  more widely.
- `assetProtocol.scope: ["**"]` — needed so the webview can play video from any
  user-chosen folder. Leave as-is.

### ⚖️ GPL obligation — resolved (now LGPL)
~~The bundled ffmpeg is GPL.~~ Resolved by the LGPL/VideoToolbox build above —
there is **no GPL component left** in the project, so no source-offer obligation
and no App-Store blocker. (Good practice: still credit ffmpeg/LGPL in an in-app
about/licence line, but it's courtesy, not a requirement.)

### Minor
`bundle.targets` scoped from `"all"` → `["app","dmg"]` (macOS-only per scope).
Android/iOS icon sets from `tauri icon` remain in the tree — harmless.

### 🟡 `cargo tauri dev` served the wrong directory — fixed
`beforeDevCommand` was `cd .. && python3 -m http.server 8080`. Tauri runs the
hook from the **repo root**, so `cd ..` overshot into the repo's *parent* — the
dev server listed `Documents/Github/` and every app asset 404'd
(`/css/styles.css` → 404 → totally unstyled page; the app actually lived at
`/dive-log/...`). Dev-only: the built `.app` (bundled `webdist`) and the
browser/Cloudflare build were unaffected. Fixed by dropping `cd ..` so the
server serves the repo root (Tauri's CWD).

### 🔴 Packaged `.dmg` was completely unresponsive — fixed (CSP nonce)
The built app rendered but **nothing was clickable** (dev was fine). Cause:
Tauri injects a CSP **nonce** into the bundled HTML, and per the CSP spec a
nonce *disables* `'unsafe-inline'` — which silently killed every inline
`onclick` handler (~130 of them) and the inline boot script. Dev was unaffected
because it loads from an external URL Tauri doesn't rewrite. **Fix:**
`app.security.dangerousDisableAssetCspModification: ["script-src", "style-src"]`
in `tauri.conf.json`, so the app's `'unsafe-inline'` stays effective in the
package. **Do not remove this** — the inline-handler architecture requires it;
removing it re-breaks the packaged app (but not dev, so it's an easy trap).

### 🟡 Folder-sync footage didn't load in the shell — fixed
Folder mode *wrote* and *deleted* `.footage.json` sidecars via the Rust fs
commands, but `loadAllSidecars` still *read* them through the browser File
System Access API (absent in the webview) — so synced footage never appeared in
folder mode (Obsidian mode was fine, it uses REST). Fixed by giving the read an
`isShell()` branch that uses the existing `read_text_file` command, matching the
write/delete paths.

### 🟡 Proxy folders — squished UI + only one remembered — fixed
Two issues surfaced testing proxies in the packaged app:
1. **Squished button:** the connect/status button and "Generate proxies…" sat
   side-by-side in the 210px video column; the long nowrap label crushed the
   status button to nothing. The proxy row now stacks vertically.
2. **Only one proxy folder remembered:** the generator drops a `proxies/` folder
   *per trip*, but the shell stored a single path — connecting one trip forgot
   the last ("only one always connected"). The shell now keeps an **array**
   (`divelog-shell-proxy-paths`, migrating the old key), scans all into the
   `_proxyUrls` pool, and "Connect" *adds* a folder. Each clip resolves its proxy
   by filename across the whole pool, so all trips stay linked.
   **Caveat:** filename-based matching collides if two folders share a filename
   (GoPro number reuse) — last scan wins; inherent to the by-filename data model.
   (Also fixed the module-load timing bug that dropped the saved path when
   `__TAURI__` wasn't injected yet — now reads `localStorage` directly.)
