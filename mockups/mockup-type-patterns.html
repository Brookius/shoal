Dive-type textures — a second channel for the ramp

rev 4 · Night/Cave reassigned · colourblind-assist toggle for worded swatches · legend question resolved

The honest finding first, because it decides everything else. I checked every place the --type-* ramp renders, and all of them already carry the type's name as adjacent text. So WCAG 1.4.1 (Use of Color) is already satisfied — colour is nowhere the only visual means of conveying which type something is. Textures are not a compliance fix. They are a glanceability improvement. That is why the default recommendation stays opt-in, and it is also why, further down, a second toggle exists for people who want the extra help even where a label is already present.

1 — Night ⇄ Cave: your swap, corrected for one collision

Night getting dots does read as a night-sky/star motif, and it's a genuine improvement — Night's mnemonic was previously blank. But a literal swap (Night takes Cave's dots, Cave takes Night's vertical) breaks the thing the whole assignment exists to guarantee:

Cave and Wall would both become vertical, and Cave/Wall is one of the 12 at-risk pairs — 0.022 ΔEok under dark protanopia, 0.034 under light deuteranopia (Cave's grey-blue and Wall's plum-rose collapse toward each other for a red-green colourblind viewer). Verified by re-running the same graph check the original assignment used, not assumed: a straight swap fails validation on exactly that one pair.

Fix: Night still takes dots — that's the part of your idea that stands on its own. Cave takes horizontal instead of vertical — Wall already owns vertical and the two are an edge, so Cave can't have it; a cave's flat sediment/rock-strata ceiling is a reasonable enough mnemonic, and horizontal is free to share with Muck (Cave/Muck isn't an edge, and the two colours — slate blue-grey vs dark olive — are nowhere near each other under either simulation).

2 — textures on worded swatches: still scoped out by default, but now a real opt-in

The previous revision found that texture behind a word looks like a bandaid (a plate spans the full width of a spine and slices it into textured/plain/textured bands) and concluded textures should apply only to swatches with no adjacent label — bars, and any future donut/legend. That conclusion stands as the default. But you're right that it shouldn't be the only option: someone who is colourblind may still want the extra scan-without-reading signal on the timeline, even though the word is technically already there and 1.4.1 is already satisfied. Reading every spine word to sort ten dive-type colours apart is real cognitive cost that a sighted user with normal colour vision doesn't pay.

So there are two controls, not one, and the second is nested under the first. The primary toggle governs wordless swatches (unchanged from rev 3, off by default). A secondary, dependent toggle — off even when the primary is on — extends texture to the three worded swatches (spine, log-form chip, dive-file hero pill) using the halo technique rather than the plate: -webkit-text-stroke in the type's own colour with paint-order: stroke fill, which follows the letterforms instead of a rectangle and produces no band/plain/band split. It was documented in rev 3 as the right mechanism if a worded surface ever needed texture; this is that surface.

4 — does the key/legend question apply? checked against the real app, not the mockup

Correction: there is no donut chart in the shipped app. The earlier revisions of this file rendered an SVG donut because an older design-exploration mockup (mockup-stats.html) sketched one, and CLAUDE colour UI.md still describes one in prose ("the donut is gestalt, the legend carries precision"). Checked against the real code just now: js/stats.js's dive-type breakdown renders only bars, via a single function, stBar() (stats.js:26) — no canvas, no SVG arcs, nothing donut-shaped exists anywhere in index.html or the JS. That's worth fixing in the colour doc separately; it isn't a texture decision, just a stale description.

Given that, the answer to "do we need a key" is no — not because a key exists elsewhere, but because there is nowhere for one to be missing. stBar() is called once per type and always writes the type's name into .st-lbl in the same row as the coloured/textured fill — read the function: the label isn't optional or conditionally rendered, it's the first thing the template builds. Every render site the primary toggle can reach (there is currently exactly one: the Stats dive-type bars) already carries its own label immediately beside the texture. There is no scenario in today's app where a user sees a pattern with nothing beside it saying what it means.

The forward-looking half of the question still matters. If a donut or any other unlabelled chart shape is ever built, that feature would need to carry its own legend before textures on it would make sense — same as it would need one for colour alone today, since CLAUDE colour UI.md's existing principle ("the legend carries precision") already requires a named legend for exactly this reason, independent of texture. So the rule to carry forward isn't "textures need a key" — it's the existing, broader one: any dive-type visual that isn't already labelled per-item needs a legend before it ships, texture or no texture. Nothing about texture adds a new requirement; it just makes the case where the requirement gets skipped more obviously wrong.

7 — recommendation

Two nested Settings controls, both off by default. Primary — "Distinguish dive types by pattern" — textures every wordless render site (today: the Stats dive-type bars only). Secondary — "Also on labelled tags," disabled unless the primary is on — extends texture to the spine/chip/hero pill via the halo technique, for anyone who wants the scan-without-reading benefit even where a label already exists.

One table, two adapters, unchanged from rev 3. TYPE_TEXTURE + the seven geometry definitions, read by a CSS-gradient adapter (bars, and the halo path reads the same table) and, if a future chart needs it, an SVG <pattern> adapter. Do not let the two representations become two tables.

No new legend work is required today, because the only real render site already labels itself unconditionally. The requirement to carry forward is the existing one — any future unlabelled dive-type visual needs its own legend before it ships, independent of whether texture is involved.

Textures — and the halo — draw in --on-type, the pair introduced for the dark ramp's spine ink, so both re-theme for free. Dark needs more alpha than light (0.58 vs 0.42).

Geometry changes ride along only while the primary toggle is on: the stat bar 9px → 14px. No donut geometry change is proposed, since no donut exists to change.

8 — what this does not fix

  • The map. Dive markers are Leaflet's default pin and carry no type colour today, so there's nothing to texture. If type-coloured pins are ever added they need to enter this system rather than invent a parallel one.
  • The underlying hue collisions. Textures are redundancy, not a fix — with both toggles off, Wreck and Muck are still 0.011 apart for a deuteranope. Rebalancing the ramp's own hues would break the mnemonics it is built on and is deliberately not proposed.
  • CLAUDE colour UI.md's donut references are stale and should be corrected separately from this texture work — they describe a chart that was never built.
